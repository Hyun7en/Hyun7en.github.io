# 0015. 분야 분류 규칙을 정하고, 트랙 순서를 빌드에서 검증한다

- 상태: 채택 ([0010](0010-curated-learning-tracks.md) 보완)
- 날짜: 2026-10-11

## 배경
글이 쌓이기 전에 로드맵 구조를 먼저 완성하기로 했다. 그런데 점검해 보니 두 가지 문제가 있었다.
1. **분류 기준이 섞여 있었다.** CS 기초에 이론(자료구조, 운영체제)과 도구(Git, Linux)가 같이 있었다. 테스트 도구는 JUnit이 Backend, Jest가 Frontend로 갈라져 있었고, MSA 같은 아키텍처 개념은 프레임워크 사이에 끼어 있었다.
2. **트랙이 `requires`와 어긋나도 빌드가 통과했다.** Spring 트랙은 REST API를 다루면서 HTTP 단계가 없었다. LLM 트랙은 RAG의 필수 선행인 벡터 DB를 곁가지로 두었다.

## 결정
- 분야 분류 규칙
  - CS 기초: 이론만 둔다.
  - 언어: 언어만 둔다.
  - 설계·테스트(신규): 언어와 무관한 엔지니어링 관행을 둔다. OOP, 디자인 패턴, 테스트와 테스트 도구, 시스템 설계, MSA가 여기에 속한다.
  - 프레임워크와 도구: 주로 쓰이는 분야에 둔다. Git·Linux는 DevOps로 옮긴다.
- 트랙의 모든 기술(줄기와 곁가지)은 직접 `requires`가 다음 중 하나에 있어야 한다. 아니면 빌드가 실패한다.
  - 앞 단계
  - 트랙의 `assumes`
  - 곁가지의 경우, 같은 단계의 줄기나 그 단계에서 먼저 나온 곁가지
- `assumes`는 트랙이 이미 안다고 가정하는 기술이다. 트랙 페이지에 "선수 지식"으로 표시한다.

## 검토한 대안
- **선행을 전이적으로 검사**: Docker → Linux → 운영체제처럼 꼬리를 물어, 모든 트랙이 CS 기초부터 시작해야 한다.
- **경고만 출력**: 빌드 로그는 아무도 읽지 않는다. 기존 검증과 마찬가지로 실패로 막는다([0003](0003-content-in-git-with-build-time-validation.md)).
- **분야를 직무 기준(roadmap.sh식)으로 재편**: 한 기술이 여러 직무에 속하게 되어, "기술마다 분야는 하나"라는 모델과 충돌한다. 직무 관점은 트랙이 맡는다.

## 결과
- 기술 86개, 분야 10개, 트랙 9개가 되었다. 새 트랙은 Python 백엔드, 모바일, 머신러닝, CS 기초다.
- 트랙을 고칠 때 빠진 선행 기술은 빌드 에러로 바로 드러난다. 그 대신 선행을 넣을지, `assumes`로 넘길지는 사람이 판단해야 한다.
